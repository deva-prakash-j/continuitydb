# ContinuityDB v0.9.1

Patch release for the fourteen findings reviewed against v0.9.0. It preserves
the existing capture approvals, identity scopes, retrieval defaults, and offline
operation. No new dependencies or automatic capture behavior are introduced.

## Upgrade from v0.9.0

1. Stop every process writing to the vault. Back up the **entire stopped vault**,
   including `index/context-vault.db`, any accompanying WAL/SHM files, canonical
   records, registry/configuration, project links, and legacy audit files.
   A record-only JSONL export is not a complete backup of feedback/audit/state.
2. Install v0.9.1 using the normal versioned installer or package workflow. Do not
   run older writers concurrently against the upgraded vault.
3. Open the vault with v0.9.1. Startup adds the canonical-write outbox and drains
   any committed pending projections. Existing record IDs and dependent data are
   retained. Rebuild is optional; it is not a required migration step.
4. Verify the version, scoped memory counts and audit status. Reconnect clients
   as usual. Re-run graph extraction to replace older cached extractor generations;
   unchanged Java files are intentionally eligible for re-extraction.

The release does not inspect, repair, or delete orphan canonical files created
by an earlier version. If prior inconsistencies are suspected, preserve a full
backup and reconcile them explicitly. Missing canonical records now stop rebuild
instead of silently deleting durable database rows. Do not delete the database
to work around that refusal.

For rollback, stop all v0.9.1 writers and restore the full pre-upgrade backup with
the previous binary. A binary-only downgrade of a mutated vault is not a supported
rollback procedure.

## Committed-but-pending recovery

A filesystem error after the SQLite commit is no longer reported as a rejected
mutation. HTTP returns status 503 with `code: CANONICAL_PROJECTION_PENDING`,
`committed: true`, and `recovery_pending: true`. MCP and CLI expose the same
outcome fields. They do not expose internal filesystem error details.

Keep the original idempotency key. Restore filesystem availability and reopen a
writable vault to replay pending projections, then retry with that same key.
Do not create a replacement capture merely because the first response was an
error. Read-only access never performs recovery or migration and can export its
committed SQLite snapshot while canonical projection is pending.

The regression suite covers process interruption and ordinary filesystem failure.
It does not claim physical power-loss durability beyond the underlying SQLite
and filesystem guarantees.

## Verification and release gates

The release candidate is checked with the full source suite, OpenAPI/client/release
validators, quality benchmark, production dependency audit, package dry-run,
generated Codex configuration probe, and native multi-round OpenCode smoke.
Standalone binaries also have ordinary and local semantic-inference smoke checks.

CI runs source tests on Node 22 and 24. The native matrix builds Linux x64,
macOS arm64, and Windows x64 with the pinned Node runtime, runs managed Windows
upgrade/rollback regressions, and checks binary/client behavior. Stable publication
requires all native builds, checksums, provenance, and the version tag to match a
commit on main. Workflow results, rather than this checklist, establish which
checks actually passed for a published artifact.

No live memory store, installed client configuration, or running service is
modified by preparing this release. A passing patch release is not a guarantee
that all possible defects have been discovered.
