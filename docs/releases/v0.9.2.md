# ContinuityDB v0.9.2

Patch release addressing all seven findings from the v0.9.1 follow-up review.
Existing approval requirements, identity scopes, retrieval defaults, and
offline-first operation are unchanged. No new dependencies are introduced.

## Fixes

| Finding | Corrected behavior |
| --- | --- |
| R2-01 | Bulk approval commits eligible proposed duplicates and keeps proposal/activation atomic. Failed canonical publication remains explicitly recoverable. |
| R2-02 | Lifecycle CLI and generated OpenCode HTTP/stdio adapters retain sanitized `CANONICAL_PROJECTION_PENDING`, `committed`, and `recovery_pending` fields. |
| R2-03 | Global OpenCode uses observation-scoped retry identities instead of permanent content keys, so new equivalent observations can refresh expired content. |
| R2-04 | Global installation pins an explicit capture-policy path, or deliberately forwards the named runtime policy setting when no path is pinned. |
| R2-05 | Automatic predecessor selection occurs atomically in the store. Delayed retries retain the original lineage and cannot revive superseded checkpoints. |
| R2-06 | Repository imports use bounded 1,000-record batches, preserve partial-progress diagnostics, and support empty incremental scans. |
| R2-07 | Detailed search repacks the final response after fallback metadata is attached. The full serialized envelope respects the existing token estimator. |

## Retry and import behavior

Global OpenCode `continuitydb_remember` returns an observation `request_id`.
By default it derives that ID from stable OpenCode session/message context and
the capture fields. Identical calls within a message are retries; a new message
is a new observation. An explicit `request_id` distinguishes intentional separate
observations within a message. If stable context is unavailable, it is required.

For every retry, including one in a later message after a committed-but-pending
error, reuse the reported `request_id` with unchanged input. This is not an update
API. Deduplication can return an existing record, and a retry does not refresh
its timestamp or lifecycle status. Durable request aliases preserve that identity
across expiry, canonical rebuild, and trusted restoration of exported records.
This does not introduce a new public import command.

Automatic checkpoint linking is an explicit `auto_link_previous` option used by
the lifecycle adapters. Direct callers retain the old strict default. An explicit
predecessor, including `null`, remains authoritative. A retry of an unchanged
superseded checkpoint is accepted as a duplicate, but reports `saved: false` and
its actual status; it never makes historical work current again.
Local, HTTP, and MCP adapters supply the resolved caller sensitivity scope to
lineage checks; an unavailable predecessor is rejected without disclosure or
creating a fork.

Repository ingestion makes each record's proposal/approval atomic, not the whole
batch or repository. Batches bound the store input to at most 1,000 records.
An error includes completed batch/record/status counts and the failed batch range.
These counts exclude the failed batch, which may itself have partially completed;
committed-pending flags describe the failing record operation, not a successfully
completed repository import. Restore availability
and retry the same Git revision and options. Existing record IDs are retained.

## Upgrade and rollback

1. Stop all vault writers and back up the **entire stopped vault**, including its
   SQLite database/WAL, canonical records, configuration, and project registry.
   Record-only exports do not include every audit/feedback datum.
2. Install v0.9.2 normally and open the vault. Additive retry-identity metadata is
   initialized automatically. Do not run older writers against the upgraded vault.
3. Refresh managed project adapters and global OpenCode installation with the
   same options and identity settings to regenerate their code. Existing generated
   plugins are not silently rewritten by installing a new binary. Use an absolute
   `--policy` path (or `CONTINUITYDB_CAPTURE_POLICY_FILE`) when installing global
   OpenCode if capture policy must remain pinned independently of launch environment.
4. Verify version, scoped record counts, and audit status. No rebuild is required.

For rollback, stop all writers and restore the complete pre-upgrade backup with
the prior binary. A binary-only downgrade after writes is unsupported because
older writers do not preserve the new retry aliases. Previously forgotten request
aliases cannot be reconstructed automatically; this release preserves new ones.

## Verification

The release gates include focused regression tests, the full source suite,
OpenAPI/client/workflow validators, quality benchmarks, dependency audit, package
checks, generated Codex configuration, and native OpenCode smoke. The native
Linux x64, macOS arm64, and Windows x64 matrix builds and verifies binaries before
stable publication, checksums, and provenance. Published workflow outcomes are
the evidence of which gates passed, not this list alone.

This release does not modify any installed runtime, live client configuration,
or live memory store automatically.
